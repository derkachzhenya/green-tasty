# Вход персонала для демонстрации

На `/staff/login` добавлена ссылка **Create a staff account** под кнопкой входа. Она открывает отдельное модальное окно регистрации персонала. По явному выбору владельца для демонстрации регистрация свободная: без приглашений и кодов из почты. Сотрудник вводит имя, фамилию, новый email, пароль и его подтверждение. После создания сразу открывается панель **48 Rustaveli Avenue**. Используйте отдельный email: существующий клиентский аккаунт не заменяется и не получает роль через регистрацию.

Рабочее место берётся из серверной настройки `STAFF_REGISTRATION_RESTAURANT=location-1`, роль всегда `waiter`. Поля роли и ID ресторана из запроса игнорируются. Доступ к другим ресторанам не выдаётся. Регистрация посетителя по-прежнему отдельная и не создаёт персонал.

Открытая регистрация включена для согласованной демонстрации (`STAFF_REGISTRATION_ENABLED=true`, также значение по умолчанию). Её можно выключить настройкой `STAFF_REGISTRATION_ENABLED=false`; вход существующего персонала и команда `staff:setup` продолжат работать. Если конфигурация кешируется, после изменения настроек выполните `php artisan config:cache`. Для этой формы новые таблицы и миграции не требуются.

Локально создан и проверен отдельный аккаунт `staff.demo@green-tasty.test`, имя **Alex Caper**, роль официанта только для **48 Rustaveli Avenue** (`location-1`). Пароль передан владельцу отдельно и в репозитории не хранится. Вход в основной локальной базе проверен через отдельный сеанс браузера: открывается панель этого ресторана. На новой базе сервера аккаунт можно создать через новую регистрацию или командой ниже (можно использовать этот же email).

По обновлённому запросу **Staff area** убран из верхней навигации. Вход персонала доступен по ссылке **Staff sign in** в обычном окне **Sign In**, через меню аккаунта и напрямую: `https://ваш-домен/staff/login` (также `/staff`).

У посетителей и персонала разные аккаунты и разные формы входа:

- **Sign In** (`/login`) — вход посетителя, затем его личные брони.
- **Staff area** (`/staff` или `/staff/login`) — отдельная форма **Staff sign in** с полями **Staff email** и **Password**, затем панель ресторана.
- В обычном окне входа также есть ссылка **Staff sign in**, а на форме персонала — **Visitor sign in**.

Форма персонала принимает только подтверждённый аккаунт с активной ролью официанта в активном ресторане. Регистрация посетителя эту роль не выдаёт. Сотрудник, случайно вошедший через обычный Sign In, тоже попадёт в панель персонала. Уже вошедший сотрудник на `/staff` видит **Open workspace**.

Клиент, открывший Staff area, видит кнопку **Switch to staff sign in**: она завершает его сеанс в этом браузере и открывает отдельную форму персонала. Его брони сохраняются. Для одновременного показа двух ролей используйте два профиля браузера либо обычное и приватное окна: авторизация использует один сеанс на профиль браузера.

## Рабочая зона персонала

После входа сотрудник видит только рабочую навигацию **Reservations / Menu**. Логотип и пункт **Staff workspace** в меню аккаунта возвращают в панель персонала. **Menu** открывает отдельный каталог своего ресторана с категориями, ценами, доступностью и описанием блюд, без клиентской корзины и кнопки предзаказа. Управление заказами остаётся в рабочей панели бронирований.

Клиентские страницы главной, ресторанов, `/book`, личных `/reservations` и `/dashboard` для вошедшего сотрудника перенаправляются в рабочую зону. Клиентские запросы на изменение бронирований и предзаказов отклоняются сервером с HTTP 403. Это ограничение сохраняется при деактивации рабочего места: сотрудник получает экран отсутствия доступа, а не клиентские права. Настройки собственного аккаунта и выход доступны. Посетители продолжают пользоваться клиентскими страницами. [Проверки разделения ролей](qa-2026-10-28/staff-workspace-ru.md).

## Подготовка на сервере

Опубликуйте актуальный код и собранные ресурсы обычным способом проекта. Эта задача не выполняет деплой. Применяйте только обычные миграции:

```bash
php artisan migrate --force
```

Если при деплое используются кешированные маршруты, пересоздайте их после обновления кода (`php artisan route:cache`), чтобы новый `/staff` был доступен.

Проверяющие могут зарегистрировать отдельный аккаунт самостоятельно через **Staff sign in → Create a staff account**. Для заранее подготовленного аккаунта по-прежнему доступна команда ниже. Подставьте свой адрес и slug уже существующего активного ресторана. Для стандартного первого ресторана это `location-1`.

Сначала можно проверить параметры без записи:

```bash
php artisan staff:setup waiter@example.test --restaurant=location-1 --create --name="Alex Caper"
```

Затем применить:

```bash
php artisan staff:setup waiter@example.test --restaurant=location-1 --create --name="Alex Caper" --apply
```

Команда выводит сгенерированный пароль один раз. Передайте проверяющим адрес сайта, этот логин и пароль лично. В репозитории и интерфейсе пароль не размещается. Созданный командой аккаунт уже подтверждён администратором и имеет роль официанта только в указанном ресторане. Аккаунт не создаётся автоматически при открытии сайта; на новой базе сервера эту команду нужно выполнить один раз.

Повторный запуск сохраняет существующий пароль. Для уже зарегистрированного аккаунта можно убрать `--create`; его email должен быть подтверждён. Команда не заменяет другую роль, не создаёт брони и не меняет клиентские заказы. Без `--apply` изменения не выполняются.

Если база на сервере новая и ресторанов ещё нет, сначала установите каталог существующей командой `php artisan menu:install` (предварительный просмотр), затем `php artisan menu:install --apply`. Не используйте `migrate:fresh`: эта команда удаляет данные.

## Как показать проверяющим

1. Дайте ссылку на главную страницу: **Sign In → Staff sign in** открывает форму персонала. Можно также дать прямую ссылку `/staff/login`.
2. Пусть проверяющий нажмёт **Create a staff account** и зарегистрируется с отдельным email либо передайте ему заранее подготовленные данные входа персонала.
3. Для проверки предзаказов создайте клиентскую бронь и отправьте предзаказ в том же ресторане. Он появится в панели сотрудника при выборе даты этой брони.
4. Клиента и официанта удобно открыть в разных профилях браузера или в обычном и приватном окнах, чтобы не переключать аккаунты.

Ссылка работает на текущем домене и не содержит `localhost` или фиксированный ID ресторана. Клиентские права доступа не меняются.
